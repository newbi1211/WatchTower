# WATCHTOWER
## 주기적 개입형 실시간 시설 운영 전략 게임

---

# 1. 게임 정의

## 플랫폼

PC Web

## 장르

실시간 시설 운영 시뮬레이션  
전략 / 경영 / 이벤트 / 협동 멀티플레이

## 플레이 인원

- 싱글플레이: 1인 + AI 운영자
- 협동 멀티플레이: 2~6인
- 동일한 게임 월드와 규칙 사용

---

# 2. 핵심 게임 경험

WATCHTOWER의 플레이어는 단순히 수치를 관리하는 관리자가 아니다.

플레이어는 실제로 움직이고 변화하는 거대한 시설을 내려다보면서 다음 행동을 반복한다.

```text
다른 작업 수행
↓
게임 화면 확인
↓
시설에서 발생한 변화 발견
↓
"무슨 일이 있었지?"
↓
시설 전체 관찰
↓
여러 사건과 문제 발견
↓
우선순위 결정
↓
5~15분 동안 집중적으로 개입
↓
시설 개선 / 확장 / 명령 설정
↓
다음 운영 계획 설정
↓
다시 다른 작업 수행
```

중요한 점은 **게임에 돌아왔을 때 항상 할 일이 여러 개 존재해야 한다**는 것이다.

---

# 3. 플레이 시간 구조

게임 플레이는 크게 두 상태로 나뉜다.

## Passive Phase

약 3~15분.

플레이어가 적극적으로 조작하지 않는 구간이다.

시설은 계속 움직인다.

- 작업자가 이동
- 차량 이동
- 물류 이동
- 시설 가동
- 건설 진행
- 연구 진행
- NPC 행동
- 사건 진행
- 환경 변화
- 적 이동
- 다른 플레이어 행동

화면을 켜놓으면 시설이 계속 움직이는 모습을 볼 수 있다.

---

## Active Phase

플레이어가 화면으로 돌아오면 시작된다.

목표 플레이 시간:

**약 5~15분**

플레이어가 처리해야 할 것이 여러 개 존재한다.

예:

```text
발전소 출력 이상
+
새로운 지역 발견
+
직원 간 갈등 발생
+
상인이 방문
+
외부 적 이동 발견
+
연구 완료
+
새 시설 건설 가능
```

따라서 게임에 한 번 돌아왔을 때 하나만 누르고 떠나는 구조가 아니다.

---

# 4. 메인 화면

게임의 메인 화면은 **시설 전체를 내려다보는 실시간 관제 화면**이다.

단순한 Dashboard 형태를 사용하지 않는다.

시설 자체가 게임 화면이다.

예:

```text
┌────────────────────────────────────────────────────────┐
│ DAY 142   14:37      전력 82%     위험도 ▲       자원 │
├────────────────────────────────────────────────────────┤
│                                                        │
│        발전구역             산업구역                   │
│                                                        │
│    ⚡ 발전기                  공장                      │
│     ▓▓▓▓                    ▓▓▓▓▓                     │
│       ↑                       ↑                        │
│     작업자                 운송 차량                   │
│                                                        │
│              중앙 거주구역                             │
│                                                        │
│      NPC들이 실제로 이동                               │
│                                                        │
│   연구구역                         방어구역             │
│                                                        │
│      🔬                                ⚠              │
│                                                        │
├────────────────────────────────────────────────────────┤
│ 사건 3     임무 2     연구 완료     건설 가능          │
└────────────────────────────────────────────────────────┘
```

# 5. 메인 화면의 핵심 원칙

숫자를 확인하는 게임이 아니라 **시설을 보고 상태를 알아낼 수 있는 게임**으로 만든다.

예:

발전 시설이 과부하 상태일 경우

숫자:

```text
출력 113%
```

뿐만 아니라 화면에서는

- 발전기가 빨라짐
- 증기 증가
- 붉은 경고등
- 기술자들이 뛰어감
- 주변 조명이 깜빡임
- 전선에 스파크 발생

등이 표시된다.

# 7. 시각적 사건 시스템

사건은 텍스트 팝업만으로 표시하지 않는다.

가능하면 **게임 월드 안에서 먼저 발생한다.**

예:

## 화재

플레이어가 화면을 확인한다.

산업 구역 한쪽에서 연기가 올라온다.

```text
공장
🔥
```

화재가 커진다.

NPC가 대피한다.

소방팀이 이동한다.

플레이어는 문제를 발견하고 클릭한다.

그제야 상세 정보가 나타난다.

---

# 8. 사건 밀도

기존 설계처럼 중요한 이벤트가 20~40분마다 발생하는 구조를 사용하지 않는다.

이벤트는 여러 규모로 발생한다.

### Micro Event

30초~3분

예:

- 작업자 부상
- 기계 고장
- 배송 지연
- 작은 화재
- NPC 요청

---

### Medium Event

5~15분

예:

- 발전기 고장
- 시설 간 갈등
- 무역선 방문
- 적 정찰대 발견
- 폭풍 접근

---

### Major Event

20~60분

예:

- 대규모 침공
- 발전소 폭발 위험
- 전염병
- 반란
- 대형 자연재해

---

### World Event

수 시간~수일

예:

- 전쟁
- 경제 위기
- 대형 재난
- 새로운 지역 개방

---

# 9. 사건 연쇄

사건 하나가 독립적으로 끝나서는 안 된다.

예:

```text
광산 사고
↓
작업자 6명 부상
↓
광물 생산 감소
↓
공장 생산 감소
↓
무역 계약 생산량 부족
↓
계약 위반 위험
```

플레이어에게 여러 선택지가 생긴다.

```text
A. 다른 광산 노동자를 이동

B. 시장에서 광물 구입

C. 생산 계약 포기

D. 부상자를 조기 복귀

E. 자동화 장비 설치
```

각 선택은 새로운 결과를 만든다.

---

# 10. 한 번 접속했을 때 행동량 증가

게임에 돌아왔을 때 다음 구조를 사용한다.

```text
복귀
↓
상황 확인
↓
문제 처리
↓
보상 확인
↓
성장 선택
↓
새 시설 배치
↓
NPC 관리
↓
탐사 명령
↓
다음 자동 운영 설정
```

즉 하나의 문제 처리 이후 바로 게임이 끝나지 않는다.

---

# 11. 복귀 보고서

플레이어가 일정 시간 화면을 보지 않았다면 복귀 시 간단한 보고가 나타난다.

예:

```text
───────────────

당신이 자리를 비운 11분 동안

✓ 철강 1,240 생산

✓ 연구 "고효율 배터리" 완료

⚠ 산업구역 사고 2건

⚠ 동쪽에서 미확인 신호 발견

★ 상인 방문

! 발전량이 최근 4분 동안 감소하고 있습니다.

───────────────

[시설 확인]
```

그러나 사건의 정답을 모두 알려주지는 않는다.

플레이어가 직접 시설을 살펴보도록 유도한다.

---

# 12. 복귀 후 발견 시스템

복귀 시 일부 정보는 의도적으로 직접 확인해야 한다.

예:

```text
"산업 구역에서 이상 활동 감지"
```

플레이어가 산업 구역을 살펴본다.

컨베이어 벨트가 정지해 있다.

원인을 확인한다.

```text
원료 공급 없음
```

물류 구역 확인.

```text
창고 과적
```

창고 확인.

```text
화물 차량 부족
```

하나의 문제를 추적하면서 자연스럽게 여러 구역을 확인한다.

---

# 13. 플레이어 행동의 세 계층

플레이어 행동을 단순 명령으로 제한하지 않는다.

## 즉각 행동

몇 초 내 실행.

- 전력 조정
- 작업자 이동
- 생산 중단
- 문 폐쇄
- 드론 출격

---

## 관리 행동

수십 초~수분.

- 시설 건설
- NPC 배치
- 생산 라인 변경
- 연구 선택
- 계약 수락

---

## 전략 행동

장기적으로 영향을 준다.

- 새로운 지역 확장
- 시설 전문화
- 세력과 동맹
- 군사 정책
- 경제 정책

---

# 14. NPC 시스템

시설에는 이름을 가진 NPC가 존재한다.

예:

```text
김도윤
발전 기술자

능력
기계 81
전기 94

특성
완벽주의
야간근무 선호
```

NPC는 게임 시스템의 일부이다.

---

# 15. NPC 사건

NPC 때문에 사건이 발생할 수 있다.

예:

```text
발전팀장 김도윤이
산업팀장 박민재와 충돌하고 있습니다.
```

선택:

```text
A. 김도윤 지지

B. 박민재 지지

C. 두 사람을 다른 구역으로 이동

D. 관리자에게 맡김
```

이후 NPC 관계가 변한다.

---

# 16. NPC 시각화

NPC는 실제 게임 화면을 이동한다.

중요 NPC는 쉽게 식별할 수 있다.

플레이어가 특정 NPC를 클릭하면 현재 행동을 확인할 수 있다.

```text
김도윤

현재 행동

발전기 03 점검 중
```

따라서 시설을 관찰하는 재미가 생긴다.

---

# 17. 탐사 시스템

시설 외부에는 미탐사 지역이 존재한다.

플레이어는 탐사팀을 보낼 수 있다.

탐사는 플레이어가 다른 일을 하는 동안 진행된다.

복귀했을 때 결과가 도착한다.

예:

```text
탐사팀 ALPHA 귀환

미확인 구조물 발견

[보고서 확인]
```

---

# 18. 탐사 중 실시간 이벤트

탐사 역시 사건을 발생시킨다.

```text
ALPHA 팀

통신:

"앞에 구조물이 있습니다."

A. 조사

B. 우회

C. 철수
```

플레이어가 없다면 사전에 설정된 AI 행동 정책이 사용된다.

---

# 19. 건설 시스템

시설은 실제로 확장된다.

초기:

```text
작은 기지
```

중기:

```text
산업 단지
```

후기:

```text
거대한 도시형 시설
```

따라서 플레이어가 자신의 성장을 시각적으로 확인할 수 있다.

# 22. 동시에 존재하는 목표

항상 여러 종류의 목표를 제공한다.

### Main Objective

장기 진행.

### Operation

몇 시간 단위.

### Mission

10~30분.

### Incident

즉각적인 문제.

예:

```text
메인

북부 지역 확보


작전

북쪽 전초기지 건설


임무

```

---

# 23. 오늘 해야 하는 이유

플레이어가 다시 들어올 이유가 존재해야 한다.

단순 로그인 보상에 의존하지 않는다.

게임 월드 자체에서 이유를 만든다.

예:

```text
6시간 후

태풍 접근
```

```text
2시간 후

무역선 도착
```

```text
오늘 22:00

적 공격 예상
```

플레이어는 이를 대비한다.

# 24. 단기적인 관심 유지

화면을 보고 있는 동안에도 짧은 변화가 계속 발생한다.

예:

- NPC 대화
- 차량 이동
- 건설 완료
- 작은 사고
- 드론 비행
- 새로운 방문자
- 경보
- 날씨 변화

모든 것이 게임 플레이 이벤트일 필요는 없다.

세계가 살아 있다는 느낌을 제공하는 역할도 필요하다.

---

# 25. 화면 이탈 방지 구조

강제로 플레이어를 붙잡아 두는 방식은 사용하지 않는다.

대신 현재 행동 다음에 자연스럽게 다른 행동이 연결되도록 한다.

예:

```text
연구 완료

↓

새 기술 획득

↓

새 시설 해금

↓

시설 건설

↓

자원 부족 발견

↓

생산라인 조정

↓

새 자원 지역 필요

↓

탐사 시작
```

이를 **Action Chain**으로 정의한다.

---

# 26. Action Chain 규칙

하나의 주요 행동은 가능한 경우 다음 행동 후보를 만들어야 한다.

예:

```text
사건 해결
→ 보상

보상
→ 업그레이드

업그레이드
→ 새로운 시설

새 시설
→ 새로운 자원 요구

자원 요구
→ 탐사

탐사
→ 새로운 사건
```

멀티플레이에서는 플레이어들이 같은 시설을 관리한다.

단순한 역할 분담만 사용하지 않는다.

# 28. 다른 플레이어의 행동 가시화

다른 플레이어가 무엇을 하는지 화면에서 볼 수 있다.

예:


# 43. 개발 최우선 검증 항목

첫 프로토타입은 그래픽 품질이 아니라 다음 질문을 검증해야 한다.

### A

5분 동안 다른 작업을 한 뒤 돌아왔을 때

**"무슨 일이 있었지?"**

라는 생각이 드는가.

### B

화면에 돌아온 뒤 최소 몇 분 동안 처리할 내용이 존재하는가.

### C

수치가 아닌 시설 화면 자체를 관찰할 이유가 존재하는가.

### D

플레이어가 명령을 내렸을 때 시설에서 눈에 보이는 변화가 발생하는가.

### E

한 행동이 자연스럽게 다른 행동으로 연결되는가.

### F

현재 작업을 끝낸 순간 다음 목표를 명확히 인지할 수 있는가.

이 조건을 만족하지 못하는 콘텐츠는 우선순위를 낮춘다.

# 44. 핵심 설계 문장

개발 AI는 게임 시스템을 추가하거나 수정할 때 다음 질문을 사용한다.

> 이 기능은 플레이어에게 새로운 것을 보여주거나, 새로운 판단을 요구하거나, 눈에 보이는 변화를 만드는가?

세 항목 모두 아니라면 핵심 게임 시스템으로 추가하지 않는다.

WATCHTOWER는 숫자를 관리하는 게임이 아니라,

**잠깐 자리를 비운 사이에도 계속 살아 움직이는 세계로 돌아와 무엇이 변했는지 발견하고, 여러 문제와 기회를 처리하고, 자신이 만든 시설의 변화를 직접 바라보는 게임**으로 설계한다.
